# Decision Register: Edge-Cloud Gateway Provisioning

This register is the authoritative traceability source for settled decisions in this change. Requirement and scenario names below are normative ownership references; implementation remains out of scope for this planning-only change.

## Settled decisions

| ID | Decision and rationale | Owning requirement / scenario | Design section | Status | Explicit boundary |
|----|------------------------|-------------------------------|----------------|--------|-------------------|
| D-01 | Keep **MySQL 8** and portable relational constraints because they meet the required model without an unrelated engine migration. | `data-model` — **Gateway control-plane records**; **Duplicate configuration version is persisted** | **Keep MySQL 8; portable uniqueness only** | Settled | PostgreSQL, TimescaleDB, JSONB-only design, and partitioning are deferred. |
| D-02 | Replace direct per-node ingest completely with one property-scoped gateway credential. | `security` — **Node authentication is separate**; **Legacy node credential is used** | **One gateway credential in `X-API-Key`; logical node in `X-Logical-Node-Id`** | Settled | No dual-auth window or proxy using node credentials. User JWT remains separate. |
| D-03 | Activate through a one-time 24-hour QR/token reference. The QR contains only an opaque reference/token, never a gateway credential; the cloud hashes it, consumes it atomically, returns the newly issued credential once, and retains audit-safe lifecycle metadata without plaintext secrets. | `gateway-provisioning` — **Single-use gateway activation**; **Gateway activates with a valid unused reference**; `security` — **Activation-token secrecy and audit safety** | **Activation reference and controlled issuance** | Settled | QR images, token plaintext, credentials, and secret-derived values are not retained in read responses, logs, fixtures, or audit records. Activation requires internet. |
| D-04 | Admin-managed global templates define expected areas, pending logical-node slots, and hardware-profile linkage. Templates are versioned and copied into a property as an independent working set before publishing that property configuration. | `gateway-provisioning` — **Global gateway templates and property copy**; **Administrator copies a template to a property** | **Global templates and property working sets** | Settled | A template does not create areas, nodes, physical bindings, or a gateway by itself. Template edits do not mutate copied property data. |
| D-05 | Use one binding vocabulary: `unbound`, `pending_initial`, `confirmed`, and `pending_reassignment`. A local technician explicitly selects a prepared pending slot/area before candidate submission; the gateway-authenticated confirmation operation can activate only that gateway's own previously submitted authorized candidate for that selected slot. A pending replacement does not displace the current confirmed binding until that confirmation. | `gateway-provisioning` — **Candidate binding, partial activation, and reassignment history**; **Gateway confirms its selected candidate** | **Canonical slot/binding state machine** | Settled | UID/serial never infers a slot. No user JWT is stored or presented by the edge gateway. Partial activation is valid; unexpected devices cannot create areas or logical nodes. |
| D-06 | Cloud configuration is authoritative, immutable when published, monotonically versioned per property, and polled/cached by the gateway. Live binding revision is separate from configuration version. | `gateway-provisioning` — **Authoritative versioned property configuration**; **Administrator publishes a revised configuration** | **Authoritative config = immutable published snapshot + live binding overlay** | Settled | Agro.io owns local cache and polling execution; IoT_Sensors publishes/accepts the contract only. |
| D-07 | Telemetry remains exactly 12 normalized fields: `null` is unavailable, `0` is measured, capture time is canonical, and anomalous times remain suspicious. | `readings` — **Payload semantics**; **Capture-time ordering and suspicious timestamps** | **Gateway ingest**; **Suspicious capture timestamps** | Settled | No static crop, size, GPS, physical-device metadata, or NDVI telemetry field. No Phase 2 expansion. |
| D-08 | Telemetry idempotency identity is **gateway + logical node + event ID**. The endpoint is implicit because telemetry has a dedicated persistence domain. | `readings` — **Gateway-scoped telemetry idempotency**; **Gateway retries an accepted telemetry event** | **Gateway ingest**; **Modified tables — `lecturas`** | Settled | NDVI has distinct scene-plus-payload replay semantics and is not part of this tuple. |
| D-09 | Latest point-sampled NDVI uses the gateway-authenticated **edge-cloud v2** NDVI contract and separate latest-point storage with Sentinel-2 provenance. | `ndvi-snapshots` — **Gateway-authorized latest-point NDVI ingestion**; **Exact NDVI replay** | **NDVI (cutover)**; **Contract v2 files** | Settled | No v1 normative reference after cutover; polygon sampling, NDVI history, and telemetry inclusion are deferred. |
| D-10 | Gateway heartbeat target is five minutes and gateway connectivity is separate from logical-node reading freshness. Cloud canonical statuses map for edge use as `inactive`/`never_seen` → `pending`, `recently_seen` → `connected`, `stale` → `delayed`, and `disconnected` → `disconnected`. | `gateway-provisioning` — **Gateway heartbeat and status**; **Gateway status mapping and reading freshness differ** | **Heartbeat last-seen columns**; **Heartbeat vs freshness** | Settled | No active inactivity alerts, notifications, or scheduler. |
| D-11 | Gateway v2 includes centrally issued update authorization and a gateway-authenticated record of local technician confirmation for a locally prepared image. | `gateway-provisioning` — **Update authorization and local confirmation**; **Prepared-image update is accepted** | **Prepared-image update authorization** | Settled | No user JWT is stored on edge. OTA delivery, automated rollback, and gradual rollout are later work. |
| D-13 | The v2 machine contract normatively specifies activation, conditional configuration polling with `304` and a live binding overlay, candidate submission, gateway confirmation, heartbeat, telemetry, NDVI, update authorization, and update confirmation, including headers, schemas, errors, and retry behavior. | `gateway-provisioning` — **Version 2 machine contract**; `readings` and `ndvi-snapshots` gateway event requirements | **Version 2 machine contract** | Settled | This change plans the contract only; it creates no physical contract files or runtime implementation. |
| D-12 | IoT_Sensors owns cloud control-plane, canonical history, and contract acceptance; Agro.io is an external paired consumer for local field workflows. | `gateway-provisioning` — **Coordinated external acceptance contracts**; **Paired edge acceptance is recorded** | **Coordinated external acceptance matrix** | Settled | No Agro.io code, services, deployment, phone helper, local UI, or outbox implementation in this repository. |

## External paired acceptance matrix

These are coordinated acceptance contracts with Agro.io, not claims that IoT_Sensors implements edge behavior.

| ID | Contracted behavior | Cloud acceptance responsibility | External owner / excluded implementation |
|----|---------------------|---------------------------------|------------------------------------------|
| X-01 | Local installation UI is available first; phone helper is deferred. | Provisioning/configuration APIs support local-screen workflows. | Agro.io local UI; mobile helper deferred. |
| X-02 | A prepared edge image activates online with the one-time reference, then polls and caches the last valid configuration. | Activation and versioned polling responses remain available and contract-stable. | Agro.io image, activation client, polling, and cache. |
| X-03 | Edge outbox retries accepted events; confirmed data is retained for 30 days; pending data is protected under disk pressure. | Telemetry/NDVI exact retries and conflicts follow their respective replay contracts; cloud accepts valid retries. | Agro.io outbox, retention, and disk-pressure policy. |
| X-04 | Gateway sends a five-minute heartbeat. | Record last accepted heartbeat and expose separate gateway status. | Agro.io heartbeat scheduler/client. |
| X-05 | Updates require central authorization plus local technician confirmation; the gateway records confirmation using its own credential, never an edge-stored JWT. | Expose the v2 authorization and confirmation boundaries. | Agro.io local prepared-image execution and technician workflow. |
| X-06 | OTA, rollback automation, and gradual rollout are later capabilities. | None in this change. | Deferred across both products. |
